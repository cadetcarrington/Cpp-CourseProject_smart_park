## 2.2.3 网页用户端功能需求

本系统的网页用户端（以下简称网页端）面向车主，运行在手机或其他带浏览器的终端上，不需要安装应用，也不需要 npm 构建：页面文件由服务端进程通过 `--web-root` 参数同源伺服，用户扫描现场张贴的二维码即可直接进入（README.md:5，README.md:94-111）。网页端与 macOS 管理端、道闸终端共用服务端的同一份停车数据，因此它既是车主自助操作的入口，也是多端一致性的直接体现。

从业务流程看，网页端的功能需求可以归纳为六个方面。第一是扫码进入与点位确认：现场二维码携带点位票据，网页端先解析票据确认车场，再引导未登录用户注册或登录（apps/webclient/app.js:693-790）。第二是账户与车牌管理：支持注册、登录、查询已绑定车牌和绑定新车牌，绑定后的车牌在预约、缴费等页面自动填充。第三是余位查询与分区展示：展示全场可用车位数、占用/预约/空闲统计，以及分区负载条和车位平面图。第四是时段预约与取消：选择车型、时长和到场时间，创建预约并即时支付定金，也可查看未结束预约并取消退款。第五是缴费收银台：查询在场记录、生成停车费订单、展示金额与二维码、倒计时超时关闭、模拟确认支付并结算离场。第六是记录与寻车：查看在场中与历史停车记录，查询到场引导和反向寻车路线。此外，网页端还提供拍照识牌辅助输入（可作为入场登记或预约车牌）、WebSocket 实时刷新、服务信息查看与退出登录。

在非功能需求上，网页端要求适配手机单列布局与刘海屏安全区，接口失败时给出可读提示，登录凭证过期后自动回到登录页；支付采用模拟网关，真实微信、支付宝支付不在 v1 范围内（README.md:182）。

## 3.1.3 网页用户端界面设计

网页端采用单页应用（SPA）结构，以下各小节均按“页面结构—主要组件—交互流程—调用接口”的顺序说明，涉及的源码集中在 `apps/webclient/` 下的三个文件中。

### 3.1.3.1 页面总体结构与视觉风格

在页面结构上，入口文件 `index.html` 仅声明字符集、移动端 viewport 和主题色等元信息，`body` 内只有 `#app` 容器、启动占位和 `#toast` 提示容器，全部界面由 `app.js` 动态生成（apps/webclient/index.html:5-15）。前端使用 hash 路由，`routes` 中登记了登录、注册、首页、预约、缴费、记录、更多和扫码八个视图（apps/webclient/app.js:257-266）；主界面由固定顶部标题栏、内容区和底部五个标签（首页/预约/缴费/记录/更多）组成（apps/webclient/app.js:285-307）。未登录访问受保护路由时统一跳转登录页，只有扫码页 `#/claim` 例外（apps/webclient/app.js:268-281）。

在视觉风格上，页面采用移动优先的单列布局，最大宽度 520 px 居中，背景为浅灰色，内容放在白色圆角卡片中，顶栏使用深蓝渐变并叠加毛玻璃效果；颜色统一由 `:root` 中的 CSS 变量定义（apps/webclient/style.css:3-15），毛玻璃只用于常驻的顶部标题栏和底部标签栏（style.css:30-40、48-57）。金额、二维码、统计格等组件的尺寸在样式表中固定下来（style.css:120-129），保证不同手机上的视觉比例一致。

在交互流程上，首屏加载时 `boot()` 先请求 `/api/v1/meta` 获取支付模式、服务端时间和 WebSocket 地址，失败时整页提示“无法连接 SmartPark 服务端”（apps/webclient/app.js:1262-1276）；WebSocket 连接成功后顶栏点亮“实时”圆点，用于说明多端数据正在实时同步（apps/webclient/app.js:232-239）。接口方面对应 `GET /api/v1/meta`。

### 3.1.3.2 扫码进入、注册与登录

在页面结构上，扫码页由现场二维码带入 `#/claim?t=<点位票据>`，未登录时只显示“扫码成功”的说明与“注册新账户/我有账户”两个按钮；登录后显示点位名、已绑定车牌信息和绑定入口（apps/webclient/app.js:693-790）。登录与注册合并为同一个页面，通过分段控件切换，账号输入框标注 2–24 个字符、密码标注 6–64 个字符的要求（apps/webclient/app.js:311-352）。

在交互流程上，扫码后票据先写入 `sessionStorage`（apps/webclient/app.js:700），这样注册成功后自动登录并回到扫码页继续绑定，无需重复扫码；绑定成功后清除票据并进入首页。已绑定车牌的账户显示“已绑定”标签和“进入用户端/再绑一辆车”，未绑定的账户输入车牌后提交“绑定并进入”（apps/webclient/app.js:742-790）。

在调用接口上，页面通过 `GET /site/resolve?t=` 解析票据并回显 `siteName`，无效票据返回 `SITE_NOT_FOUND`（404），过期或撤销的票据返回 `SITE_EXPIRED`（410）（src/network/RestGateway.cpp:1671-1701）。注册调用 `POST /auth/register`，该接口返回 201 且不携带 token，前端随后再调用 `POST /auth/login`（tests/e2e_rest.sh:179-186）；车牌管理调用 `GET /me/plates` 与 `POST /me/plates`，重复绑定保持幂等（src/network/RestGateway.cpp:1728-1760）。登录成功后 token 与用户信息写入 `localStorage`，所有请求由统一的 `api()` 函数附加 `Authorization: Bearer` 头（apps/webclient/app.js:98-119、138-146），遇到 401 自动登出并回到登录页。

### 3.1.3.3 余位查询与分区展示

在页面结构上，首页自上而下依次是余位总览卡、分区负载卡、车位图卡和快捷操作卡（apps/webclient/app.js:356-414）。主要组件包括 44 px 的可用车位数、占用/预约/空闲/总数四格统计、按分区绘制的负载条，以及 460×340 的 canvas 车位图与图例（apps/webclient/app.js:381-407、1003-1010）。

在交互流程上，进入首页即请求 `GET /parking/status` 渲染余位，再异步请求 `GET /layout` 绘制车位图；布局加载失败时静默隐藏车位图卡片，余位数字不受影响（apps/webclient/app.js:395-403）。车位图由 `drawLayout()` 按 0.5 m 栅格比例绘制底图、区域、障碍、车位编号和出入口，车位按状态着色：占用为红色、预约为橙色、停用为灰色、普通与无障碍车位为绿色、充电车位为蓝色、VIP 车位为紫色，入口为蓝色、出口为橙色（apps/webclient/app.js:971-980、1030-1249）；`prepareCanvas()` 按 `devicePixelRatio` 放大画布后备存储，避免高分屏绘制模糊（apps/webclient/app.js:1015-1026）。

在调用接口上，`GET /parking/status` 返回 `available`、`capacity`、`occupied`、`reserved` 与 `zones`，`GET /layout` 返回场地尺寸、区域、障碍、车位、出入口等绘制数据，车位状态以 0 空闲/1 占用/2 预约/3 停用表示（apps/webclient/app.js:995）。

### 3.1.3.4 时段预约与取消

在页面结构上，预约页由预约表单卡和“我的未结束预约”列表卡组成（apps/webclient/app.js:444-557）。主要组件包括车牌输入框、车型下拉（`car` 轿车、`electric` 新能源、`motorcycle` 摩托车、`truck` 货车）、时长下拉（30/60/120/180/240 分钟，默认 120 分钟）、`datetime-local` 到场时间、无障碍车位复选框与“创建预约（付定金 ¥20）”按钮（apps/webclient/app.js:451-471）。

在交互流程上，默认到场时间取当前时间 45 分钟后并向上取整到 15 分钟格，保证始终满足提前量（apps/webclient/app.js:446-449）；提交前校验至少提前 30 分钟（`RESERVE_MIN_LEAD_MS`，apps/webclient/app.js:435）且不超过 7 天（`RESERVE_MAX_ADVANCE_MS`，apps/webclient/app.js:436），不满足时在列表区显示提示而不发出请求（apps/webclient/app.js:495-509）。预约成功后页面显示车位号、定金金额、定金订单凭证号、入场步行距离与转弯数（apps/webclient/app.js:520-527）；未结束预约通过 `GET /reservations?plate=&state=open` 加载，取消时需要二次确认，确认框明确提示“定金将全额退回”（apps/webclient/app.js:530-555）。

在调用接口上，创建预约调用 `POST /reservations`，请求体为 `{plate, vehicleType, startMs, durationMin, accessible}`；服务端规则校验失败返回 409 `CONFLICT` 并附带原因，前端原样展示。定金在创建预约时由核心层即时收取，网关同时落一张已支付的 `deposit` 订单作为支付凭证（src/network/RestGateway.cpp:946-1017，docs/rest-api.md:109-139）。预约的完整状态机与到场核销见 4.2.2 节。

### 3.1.3.5 缴费收银台

在页面结构上，缴费页由车牌查询卡、“在场车辆”信息卡和“最近缴费单”列表卡组成；点击“生成缴费单”后，信息卡区域整体替换为收银台卡片（apps/webclient/app.js:561-632）。主要组件包括大号金额、150×150 的支付二维码、等宽字体的订单号、支付倒计时、确认支付按钮以及一段“模拟网关”的说明文字（apps/webclient/app.js:633-660）。

在交互流程上，先查询在场记录并显示车位、入场时间、已停时长和预计费用（apps/webclient/app.js:600-612），再生成缴费单（apps/webclient/app.js:613-624）。收银台倒计时以订单 `expireAtMs` 为基准，每 500 ms 刷新一次，归零后显示“订单已超时关闭”并禁用支付按钮（apps/webclient/app.js:650-663）。确认支付成功后页面显示“支付成功，已放行”、实付金额、停用车位与本次时长，并提供跳转停车记录的链接（apps/webclient/app.js:665-685）。

在调用接口上，查询在场记录调用 `GET /records/{plate}/active`，生成订单调用 `POST /payments/orders`（仅支持 `kind=parking_fee`），确认支付调用 `POST /payments/orders/{id}/confirm`；最近缴费单调用 `GET /payments/orders?pageSize=8`，状态映射为 `paid` 已支付、`pending` 待支付、`expired` 已超时、`refunded` 已退款、`cancelled` 已关闭，类型映射为 `deposit` 预约定金、`parking_fee` 停车费（apps/webclient/app.js:574-589）。收银台二维码内容为 `SMARTPARK-PAY:<outTradeNo>`，由服务端 `/api/v1/qr` 接口生成（apps/webclient/app.js:640-642）。

### 3.1.3.6 停车记录、到场引导与反向寻车

在页面结构上，停车记录页用“在场中/历史”两个标签切换，请求 `GET /records?state=active|closed&pageSize=50`；每个条目显示车牌、车位与入场时间，历史记录额外显示离场时间、费用和时长，在场记录则显示“进行中”（apps/webclient/app.js:798-843）。

到场引导与反向寻车放在“更多”页：输入车牌后并发请求 `GET /guide/{plate}` 与 `/layout`，在同一张 canvas 上绘制车位图并叠加路线折线动画（apps/webclient/app.js:934-960、1251-1258）。在场车辆返回反向寻车结果，页面提示“反向寻车：前往 <车位>（<分区> 区），从入口步行约 <距离> 米、<转弯数> 个转弯”；存在未开始预约时返回到场指引，提示预约车位与入场步行距离（apps/webclient/app.js:953-954）。无在场记录且无有效预约时，接口返回 404，页面提示“该车牌无在场记录或有效预约”。

“更多”页还提供拍照识牌辅助功能：前端用 canvas 把照片压缩到长边 900 px 后调用 `POST /lpr/recognize`，识别成功显示车牌、后端模式（`mock`/`script`）、置信度与号牌颜色，并可一键“用作入场登记”或“用作预约车牌”；识别失败时区分 `NO_PLATE`（画面中未找到车牌）与 `LPR_FAILED`（识别脚本出错）给出不同提示（apps/webclient/app.js:856-928）。服务信息卡展示支付模式、实时推送状态、当前账号与退出登录入口（apps/webclient/app.js:876-885）。

### 3.1.3.7 响应式布局与浏览器兼容

在布局上，页面最大宽度 520 px 并水平居中，底部标签栏固定，内容区底部预留 76 px 避免被遮挡（apps/webclient/style.css:26、48-57）；标签栏使用 `env(safe-area-inset-bottom)` 适配 iPhone 底部安全区（style.css:55）；表单与快捷按钮使用两列网格，窄屏下自动压缩。对于不支持 `backdrop-filter` 的浏览器，顶栏与标签栏回退为不透明背景（style.css:166-171）；canvas 按设备像素比放大，保证高分屏清晰（apps/webclient/app.js:1015-1026）。

在浏览器兼容上，网页端只使用原生 ES2017 能力（`async/await`、`fetch`、`WebSocket`），没有打包步骤和框架依赖，Chrome、Safari 与微信内置浏览器均可直接打开。服务端为静态页统一附加 CSP、`X-Content-Type-Options`、`Referrer-Policy`、`X-Frame-Options` 等安全头（src/network/RestGateway.cpp:113-132），其中 CSP 只允许同源脚本与样式，因此前端不使用 CDN 和内联脚本；未匹配路径回退到 `index.html`，刷新子路由不会出现 404（src/network/RestGateway.cpp:361-412）。

在网络异常处理上，WebSocket 断开后按 1 秒、2 秒、4 秒的间隔指数退避重连，上限 15 秒，心跳间隔 20 秒（apps/webclient/app.js:170-177、211-215）；HTTP 请求的网络错误统一提示“无法连接服务器”，不会让页面停在无反馈的加载状态。

## 4.1.2 网页用户端操作演示

演示前提是服务端已经用 `--web-root apps/webclient` 启动，并用 `--advertise` 指定手机可以访问的局域网地址；启动成功的横幅会打印网页接入地址的二维码（apps/server/main.cpp:956-980、1056-1065），完整部署参数见 4.1.3 节。手机与运行服务端的 Mac 处于同一局域网后，按以下步骤操作。

1. 扫码进入。用手机相机扫描服务端横幅中的二维码，地址形如 `http://<IP>:18080/#/claim?t=<票据>`。预期：页面进入“扫码进入”页，未登录时显示“扫码成功”以及“注册新账户/我有账户”两个按钮；若扫描的是已经撤销或过期的票据，页面显示“二维码无效或已被撤销，请扫现场最新的码”，并提示重新扫码。

2. 注册与登录。点“注册新账户”，输入账号 `user2`（2–24 个字符）与口令 `smartpark123`（6–64 个字符）。预期：注册成功后自动登录并回到扫码页；若账号已存在，页面提示冲突并停留在注册页，此时可改用“我有账户”登录。

3. 绑定车牌。在扫码页输入车牌 `京A12345`，点“绑定并进入”。预期：提示“京A12345 已绑定到本账户”并进入首页；再次扫描同一二维码时，页面显示“该账户已绑定车牌”和“进入用户端/再绑一辆车”按钮。

4. 查看余位与分区。首页顶部显示当前可用车位数与总车位数（使用 `data/garage-6f.txt` 演示布局时为 75 个车位），下方是占用/预约/空闲/总数四格统计、分区负载条和车位图。预期：空闲车位为绿色、占用为红色、预约为橙色，入口与出口分别标注；若此时在管理端或道闸终端执行一次入场，网页端会通过 WebSocket 收到事件并自动刷新，顶栏“实时”圆点保持点亮。

5. 时段预约。切到“预约”页，默认到场时间为当前时间 45 分钟后且已对齐 15 分钟格；选择 2 小时时长并提交“创建预约（付定金 ¥20）”。预期：列表区显示车位号、定金金额、定金订单凭证号，以及“步行约 X 米 / Y 个转弯”；把到场时间改到 10 分钟后再次提交，页面提示“预约需至少提前 30 分钟”且不发出请求；勾选“无障碍车位（免定金）”后定金为 0，可用于演示免定金分支；点击“取消”并确认后提示“已取消，定金退回”。

6. 停车缴费。在另一终端让车牌 `京B67890` 入场，然后在“缴费”页输入该车牌并点“查询在场车辆”。预期：显示车位、入场时间、已停时长和预计费用（入场不足 30 分钟时显示 ¥0.00）；点“生成缴费单”后出现模拟收银台，包含金额、二维码、订单号和“支付剩余 MM:SS”倒计时。等待 15 分钟不操作，倒计时归零后支付按钮不可用并显示“订单已超时关闭”；重新生成订单后点“确认支付（模拟）”，页面显示“支付成功，已放行”、实付金额、停用车位和本次时长，首页可用车位数加一，记录页历史中出现该车的已离场记录。

7. 到场引导与反向寻车。进入“更多 → 反向寻车/到场指引”，先输入在场车牌 `京B67890` 查询。预期：canvas 显示车位图并高亮行驶路线，下方文字为“反向寻车：前往 <车位>（<分区> 区），从入口步行约 <距离> 米、<转弯数> 个转弯”；再输入一个有未开始预约的车牌，提示变为“到场指引：预约车位 …，入场步行约 … 米”；输入无效车牌则提示“该车牌无在场记录或有效预约”。

8. 拍照识牌（可选）。在“更多 → 拍照识牌”中选择一张车牌照片。预期：先显示“识别中…（首次约 10–20 秒，请稍候）”，随后显示车牌、后端模式（`mock` 或 `script`）与置信度，点“用作入场登记”可直接完成入场；照片中没有车牌时显示 `NO_PLATE` 提示与拍摄建议。

## 4.2.3 计费与模拟支付实现

停车费由服务端统一计算。默认计费规则为免费 30 分钟、以 30 分钟为一个计费单元、首个单元最低收费 2.5 元、此后每个单元 2.5 元、单次封顶 100 元（src/core/service/Billing.h:7-13）。`calculateFee()` 先排除零时长与非法计费单元，时长不超过免费时长时返回 0；超出后按“不足一个单元按一个单元”向上取整计算单元数，只有一个单元时收最低消费，之后按单元累加并封顶（src/core/service/Billing.cpp:14-43）。因此停车 30 分钟以内免费，31 分钟收 2.5 元，61 分钟收 5 元，累计到 100 元后不再增加。计费只在服务端下单时快照一次，前端显示的预计费用同样来自接口返回，浏览器不参与计费。

支付订单保存在网关层的 `payment_orders` 表中，字段包括订单号、商户订单号（唯一）、类型（`deposit` 或 `parking_fee`）、用户名、车牌、预约号、金额、状态、创建/过期/支付/退款时间和扩展载荷（src/network/RestGateway.cpp:494-510）。订单号由 `po_` 加 6 字节随机十六进制生成，`outTradeNo` 规则为 `SP + yyyyMMdd + 订单号后缀`；停车费订单的金额按在场记录时长快照，初始状态为 `pending`，过期时间取创建时间加 15 分钟（src/network/RestGateway.cpp:1189-1201，src/network/RestGateway.h:44）。订单状态迁移如下表所示。

| 当前状态 | 触发动作 | 结果状态 | 说明 |
| --- | --- | --- | --- |
| `pending` | 用户确认支付且离场结算成功 | `paid` | 同一请求内完成离场并返回结算结果 |
| `pending` | 超过 `expireAtMs` 仍未支付 | `expired` | 服务端每 15 秒扫描一次关单 |
| `pending` | 车辆已从出口按未缴费方式离场 | `cancelled` | 避免出口与收银台重复收费 |
| `paid` | 再次确认支付 | `paid` | 幂等返回当前订单，不二次扣款 |
| `paid`（定金单） | 取消预约或爽约 | `refunded` | 由预约流程生成退款或没收凭证 |

收银台二维码的内容是 `SMARTPARK-PAY:<outTradeNo>`，由服务端 `/api/v1/qr?text=` 接口生成 SVG 图片，该接口免认证以便浏览器 `<img>` 直接加载。超时关闭由网关的定时器负责：每 15 秒扫描一次全部订单，把 `pending` 且已过期的订单置为 `expired`，并通过 WebSocket 广播 `payment.expired` 事件（src/network/RestGateway.cpp:163-164、1942-1959）。前端的倒计时只负责展示剩余时间和禁用按钮，订单的最终状态始终以服务端为准（apps/webclient/app.js:650-663）。

防重复支付由多层约束共同保证。确认接口对已支付的订单直接返回当前订单载荷，不产生第二次扣款（src/network/RestGateway.cpp:1247-1250）；非 `pending` 状态的订单返回 409 `PAYMENT_STATE`（src/network/RestGateway.cpp:1252-1257）；定金订单不允许手工确认，只能随预约自动结算（src/network/RestGateway.cpp:1258-1262）；若结算时车辆已不在场，则把订单置为 `cancelled` 并返回错误（src/network/RestGateway.cpp:1266-1271）；车辆从出口正常离场时，网关会关闭该车牌其余未支付的停车费订单；用户已人工支付的 10 分钟内也不再触发无感扣费（src/network/RestGateway.cpp:1275、1364-1373）。此外，定金与停车费分为两层：定金由核心层 `FakePaymentGateway` 在创建预约时即时收取，网关只落一张已支付的 `deposit` 凭证，取消或爽约的退款由预约流程对应生成，网页端不重复构造定金支付。

支付成功后的业务结算与支付确认在同一个请求中完成。服务端调用 `performLeave()` 执行离场：释放车位、生成已关闭的停车记录、落库费用与时长，再把订单更新为 `paid` 并记录支付时间；随后通过 WebSocket 广播 `payment.paid` 与 `parking.exited`，返回值包含 `{order, leave}`，其中 `leave` 提供车位、费用、时长和进出场时间，前端据此展示“支付成功，已放行”并跳转记录（src/network/RestGateway.cpp:1263-1288、1334-1383）。若订单状态与停车记录状态不一致，一律以服务端离场结果为准，前端不做本地状态推断。

## 附B 网页端问题与经验

- 单页应用回退时，响应的 MIME 类型必须按实际送出的 `index.html` 计算，而不能按请求路径计算。否则请求 `/some-route` 会得到 `application/octet-stream`，配合 `nosniff` 后浏览器拒绝渲染，刷新子路由即白屏（src/network/RestGateway.cpp:392-406）。

- 图片识牌如果同步等待外部进程会阻塞服务端事件循环：旧实现用 `waitForFinished`，实测识别 13.3 秒期间 `GET /parking/status` 要等 12.3 秒，还会让管理端错过心跳（docs/rest-api.md:169-170）。改为异步识别后，识别进行中状态查询仍能在 1.5 秒内返回，这条约束已写进端到端测试（tests/e2e_rest.sh:460-484）。

- 定金与停车费必须分层处理：定金由核心层在创建预约时即时收取，网关只落一张已支付的凭证；网页端只开放停车费手工下单，避免同一笔费用被构造两次（src/network/RestGateway.cpp:1177-1182）。

- 倒计时采用“前端展示、后端权威”的双轨方式。前端按订单过期时间显示剩余秒数并在归零时禁用按钮，真正的关单由服务端定时扫描兜底，避免用户关闭页面后订单一直停留在待支付状态（apps/webclient/app.js:650-663，src/network/RestGateway.cpp:1942-1959）。

- 同源部署显著简化了前端实现：页面、接口和 WebSocket 由同一进程提供，前端无需处理跨域与 token 跨域携带，CSP 也可以收紧到只允许同源资源（src/network/RestGateway.cpp:113-132、361-412）。

- 所有渲染到页面的动态文本都经过 `esc()` 转义，车牌、账号等用户输入不会直接拼进 HTML，降低了注入风险（apps/webclient/app.js:44-48）。
