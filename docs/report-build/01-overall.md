# 第一章 绪论

本报告介绍 SmartPark 智能停车场管理系统的需求分析、系统设计与测试验证过程。报告内容覆盖 macOS 管理端、统一服务端和网页用户端三个部分，以及三者之间的接口协同关系。道闸终端与命令行用户端作为现场演示的辅助程序，只在必要处提及，不作为独立章节展开。

## 1.1 课程设计目的

本次课程设计以“程序设计综合实践”课程所学内容为基础，要求完成一个具有完整业务流程和实际应用背景的软件系统，并按照软件工程的规范编写设计报告。具体目的包括以下四个方面。

第一，综合运用 C++ 语言、数据结构与算法、数据库、计算机网络和软件工程等课程知识，把分散的课堂内容组织成一个可运行、可演示、可测试的完整项目。第二，经历“需求分析—总体设计—详细设计—编码实现—测试验证—文档总结”的完整开发过程，理解各阶段之间的衔接关系，而不只是停留在编写单个程序或完成单道算法题。第三，掌握桌面端、服务端和网页端三类程序的开发方法：使用 AppKit 与 Objective-C++ 编写 macOS 原生界面，使用 C++17 编写业务核心与网络服务，使用原生 HTML、CSS 和 JavaScript 编写无需构建的网页用户端。第四，培养工程规范意识，包括分层设计、接口与协议先行、异常处理、数据持久化、自动化测试和版本管理等，为后续课程学习和工程实践打下基础。

## 1.2 课程设计背景

随着城市机动车保有量持续增长，商业综合体、医院、写字楼等场所的地下停车场规模越来越大，车位数从几十个增加到数百个，出入口也从单进单出发展为多进多出。传统停车场依赖人工发卡、人工收费和固定指示牌，存在三类突出问题：一是车主进入地库后难以快速找到空闲车位，绕行造成拥堵和尾气排放；二是高峰时段出入口排队，人工收费效率低；三是车位、预约、收费等数据彼此割裂，管理方难以掌握实时占用和收入情况。

智慧停车系统通过车位状态采集、车位引导、时段预约、电子支付和反向寻车等功能，把“入场—停车—缴费—离场”的整个链条数字化。本次课程设计的选题来源于一张真实的三塔楼地下车库平面图纸：按图纸重建的布局文件尺寸为 165 m × 85 m，划分为 10 个车位分区，布置 330 个车位，设置 1 个入口和 2 个出口，图纸中还有 9 处核心筒、楼梯井等不可通行的障碍物。本组以该图纸为数据基础，设计并实现了一个多端协同的停车场管理系统，用于演示从车辆入场、车位分配与路径引导、时段预约、计费支付到离场结算的完整业务流程，并接入真实的图片车牌识别能力。

## 1.3 课程设计要求

课程设计要求完成一个功能完整、结构清晰、可独立运行和演示的程序，并提交符合模板规范的课程设计报告。结合选题，本组确定的需求如下。

功能方面，系统应支持车辆入场与离场、车位自动分配与路径引导、时段预约与到场核销、停车计费与模拟支付、停车记录查询与运营统计、图片识牌与人工核对等功能，并保证 macOS 管理端、网页用户端和现场终端看到的是同一份停车数据。

技术方面，要求使用 C++17 实现业务核心，使用 SQLite 完成数据持久化；服务端同时提供 TCP、REST 和 WebSocket 三类接口，供不同终端接入；macOS 管理端采用原生 AppKit 实现，不使用 Qt Widgets；网页用户端采用原生前端技术实现，不依赖 npm 构建；车牌识别使用 YOLO 检测与 PP-OCRv5 识别模型。

质量方面，要求项目能够通过 CMake 预设完成构建，具备单元测试、集成测试和端到端测试；对异常输入、重复操作、超时订单、断网重连等情况有明确处理；数据库重启后能够恢复停车记录、预约、定金和支付订单等关键数据。

文档方面，要求按照学院报告模板撰写需求分析、系统设计、测试验证和设计总结，做到事实准确、图表规范、代码引用可追溯。

# 第二章 需求分析

## 2.1 问题描述

本系统面向地下停车场的日常运营，参与角色包括车主、停车场管理员和现场道闸设备。车主通过手机扫码进入网页用户端，完成注册登录、绑定车牌、查询余位、预约车位、缴费和反向寻车；管理员通过 macOS 管理端查看实时车位图、处理车辆入场离场、管理预约和查询运营数据；道闸终端在出入口采集车牌并与服务端交换事件。三类角色操作的是同一份停车数据，这是需求分析首先需要明确的约束。

从业务流程看，系统需要解决以下问题。第一是入场选位问题：当车辆到达入口时，系统要根据车型、车位类型、分区负载、入口距离、出口距离、通道拥堵和转弯次数等因素选出合适的车位，并给出一条可通行的行驶路线；当车辆在库内需要应急让位或管理员需要查询时，还要能根据当前位置重新规划路线。第二是预约问题：车主可以提前预约某个时段的车位，系统必须校验预约提前量、时长和时段冲突，在合适时机锁定物理车位，并处理到场核销、取消退定金、爽约没收定金和离场抵扣等分支。第三是计费与支付问题：车辆离场时需要按免费时长和计费单元计算停车费，生成支付订单并展示二维码，支付成功后自动结算离场；订单存在超时关闭、重复确认、支付后退款等情况，必须保证订单状态和停车记录状态一致。第四是多端一致性问题：管理端、网页端和道闸终端可能同时操作同一辆车，服务端必须作为唯一权威数据源，通过事件推送把变化同步给各终端；网络中断时道闸还要能缓存事件并在恢复后补报。第五是可验证性问题：系统的核心算法、网络协议和界面交互都需要通过自动化测试或可复现的操作步骤来验证，而不是只靠人工观察。

## 2.3 程序难点与解决

本系统涉及图形界面、路径规划、并发网络、数据持久化和机器学习模型集成等多个技术方向，实现过程中遇到的主要难点及解决思路如下。

（1）多约束条件下的车位分配与路径规划。系统先按入口距离、出口距离、拥堵、转弯、车型和分区压力评分，再用带方向状态的栅格搜索一次求出多个候选车位的最优路线。搜索复用线程级缓冲区，并在后台线程处理普通入场；提交前校验配置与车位快照，状态变化时最多重试两次，避免大地图计算阻塞界面和网络事件循环。

（2）地库图形的绘制与交互。管理端的停车地图需要绘制 330 个车位、分区边界、障碍物、入口出口、路线和车辆标记，并支持缩放、平移、点击选中和反向寻车高亮。解决方法是自定义 NSView 子类，在 drawRect 中按世界坐标到视图坐标的变换统一绘制，路线的折线只保留拐点以减少绘制量；交互事件先做坐标反变换再命中测试，避免把界面逻辑和业务数据耦合在一起。

（3）多端数据一致性与断网恢复。管理端本地模式直接操作数据库，远程模式通过 TCP 访问服务端，网页端通过 REST 和 WebSocket 访问服务端，道闸终端还有离线缓存需求。解决方法是把停车业务集中在服务端的一个业务实例中，TCP 与 REST 共用同一实例，任何状态变化都通过事件中心发布给 TCP 客户端和 WebSocket 订阅者；道闸只把服务端明确确认过的事件从离线队列中移除，重连后按顺序补报，服务端按事件标识去重。

（4）图片识牌的工程化。识牌需要依次完成车牌检测、四角定位与透视矫正、字符识别，模型推理耗时远高于普通业务逻辑，且并发请求容易把服务端拖慢。解决方法是把推理放在独立进程或线程池中执行，对请求做并发限制和超时保护，识别结果只作为入场建议，最终由管理员人工核对确认，识牌失败不影响正常业务流程。

（5）支付与离场结算的一致性。支付订单可能被重复确认、可能超时、可能在支付后申请退款，而停车记录只能结算一次。解决方法是设计明确的订单状态机，确认支付时先做幂等判断，再在同一个业务流程中完成结算离场和事件发布；对已人工缴费的车辆设置短时保护，避免无感扣费重复产生订单。

（6）预约状态机的分支处理。预约需要区分已创建、已锁定、已核销、已取消、已爽约等状态，还要处理定金支付、抵扣和超时释放。解决方法是在服务层集中维护状态迁移表，所有入口（管理端表单、网页、命令行终端）共用同一个 Reservation 模型和同一套校验逻辑，避免各端各自实现导致口径不一致。

（7）测试的可重复性。界面程序、网络服务、定时任务和模型推理都不容易直接断言。解决方法是对业务核心做依赖注入，用假的支付网关、假时钟和可控的随机源编写单元测试；对服务端启动真实进程做端到端测试；对管理端远程模式使用模拟服务端验证数据刷新和操作路径。

# 设计总结

本次课程设计完成了一个以 C++17 为核心、由 macOS 管理端、统一服务端和网页用户端组成的智能停车场管理系统。系统以一张 165 m × 85 m、330 个车位的三塔楼地下车库图纸为数据基础，实现了车辆入场、车位分配与路径规划、时段预约与定金、停车计费与模拟支付、图片识牌、多端同步与断网补报等功能。核心代码 src/ 目录约 1.26 万行，网页用户端 app.js 约 1276 行，SQLite 共 12 张表，REST 端点 34 个，注册的 CTest 测试项 12 个，开发周期内提交记录 109 次。

在技术实现上，本设计坚持“业务只有一份、界面各端适配”的思路：停车业务集中在 src/core 的核心类中，服务端通过 TCP、REST 和 WebSocket 对外提供统一能力，管理端本地模式直接复用同一套核心，远程模式、网页端和现场终端通过协议访问服务端。这样既保证了功能一致，也便于测试和部署。界面方面，macOS 端使用 AppKit 原生控件和自绘视图完成实时车位图、图表和表格展示；网页端使用原生 HTML、CSS 和 JavaScript 实现单页应用，通过二维码贴纸完成扫码进入，无需安装客户端。

课程设计过程中遇到的问题及解决情况如下。

一是路径规划的性能问题。系统把“逐车位搜索”改为一次多目标搜索，并复用搜索缓冲区；普通入场进一步改为后台计算、快照校验和有限重试，使大地图规划不再阻塞界面与网络事件循环。

二是地库图形的绘制与交互问题。图纸中车位、通道、障碍物数量多，直接按屏幕坐标绘制会导致缩放和平移后位置错乱，点击也容易命中错误的图元。最终采用世界坐标统一建模、绘制时统一变换、事件时反向变换的方式，才把图形显示和交互逻辑分开。

三是多端一致性问题。管理端、网页端和道闸同时操作时，曾出现界面显示与数据库不一致、网页端新建的预约在远程管理端看不到、道闸断线重连后重复补报等情况。排查后发现问题分别出在事件通道和补报确认方式上：前者是因为 TCP 服务端没有订阅事件总线，改为由事件中心统一向 TCP 与 WebSocket 双通道广播后，跨入口一致性得到保证；后者是因为只按“整批成功”删除队列，改为服务端逐条返回结论、终端只删除队首连续成功的前缀，并配合“车牌+事件类型+毫秒时间戳”的去重规则，补报才具备幂等性。

四是识牌的工程化问题。模型推理的耗时与显存占用和普通业务逻辑差异很大，早期在请求线程内同步等待脚本结束，实测一次识别耗时 13.3 秒，期间状态查询被阻塞 12.3 秒并导致管理端错过心跳。改为“临时图片 + 独立进程 + 看门狗 + 并发队列”的异步模型后，识牌不再影响在线业务，识别进行中状态查询仍能在 1.5 秒内返回，识别失败时则降级为人工输入车牌。

五是支付状态一致性问题。订单可能被重复点击确认、可能超时关闭，也可能在支付完成后车辆已经离场。通过订单状态机、确认支付时的幂等判断、支付与结算在同一流程内完成，以及对已缴费车辆设置短时保护，避免了重复扣费和状态冲突；前端倒计时只负责展示，真正关单仍由服务端定时扫描兜底。

六是预约的分支处理问题。预约涉及锁位、核销、取消、爽约和定金抵扣，分支多且容易遗漏，早期实现只锁“当前时段”，同一车位可能同时存在两笔有效预约。通过把状态迁移集中到预约服务中、创建即锁位、加唯一部分索引并在重启时对账修复，各入口行为不一致和“双主”问题才被消除。

七是 macOS 端的框架共存问题。管理端使用 AppKit 界面，同时又要复用 Qt 的网络与 SQL 模块，两套事件循环需要显式协作：程序没有使用 `NSApplicationMain`，而是手工创建应用对象，再用一个短周期定时器调用 `processEvents`，缺少这一步时远程连接会一直停在“正在连接”；此外以纯代码构建界面时还必须手工安装主菜单，否则标准编辑快捷键会失效。

八是网页单页应用的路由回退问题。用户刷新子路由时，服务端必须把 `index.html` 作为回退内容返回，并按实际送出的内容计算 MIME 类型；若按请求路径计算类型，页面会被浏览器以类型不符为由拒绝渲染而白屏。把回退与同源部署统一交给服务端处理之后，刷新任意子路由都能正常进入。

通过本次课程设计，本组成员在以下方面收获较大：一是理解了从需求到交付的完整工程流程，认识到接口设计、异常处理和测试用例与功能代码同样重要；二是掌握了 C++ 服务端编程、Qt 网络与 SQL 模块、AppKit 界面和原生前端等多个技术栈的组合使用方法；三是体会到“先数据与协议、后界面与算法”的设计顺序可以显著减少返工；四是认识到性能问题必须通过测量来定位，而不是凭感觉优化。

本设计仍有不足和可改进之处：真实支付渠道和道闸硬件尚未接入，目前使用模拟网关与道闸状态机替代；识牌在复杂光照和污损车牌下的准确率仍有提升空间；远程模式下管理端的布局编辑、分配策略切换等功能尚未开放；运营分析中的趋势预测和智能分析接口还停留在可注入的框架层面。后续可以接入真实支付与硬件、扩充识牌训练数据，并完善远程管理能力。
